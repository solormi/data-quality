## 1. 表基本信息

| 维度 | 取值 |
|------|------|
| 表名 | `ods_member_info_scd` |
| 表类型 | ODS(贴源) |
| 数据形态 | 会员主档 SCD(慢变化维表) |
| 用途 | DWS 月度任务用它确定"本月月初那一刻,有谁是有效会员" |
| 分区键 | `create_time`(DATE) |
| 表模型 | SCD 拉链 |

## 2. 字段特征

### 2.1 字段:`tenant_id`

- **类型**:BIGINT
- **业务语义**:租户编号,多租户系统下唯一标识一个租户
- **取值约定**:固定枚举值,目前活跃租户 100001、100002 等
- **NULL 语义**:业务上不允许 NULL
- **单位 / 精度**:无
- **特殊值**:无
- **已知异常**:无

### 2.2 字段:`user_id`

- **类型**:BIGINT
- **业务语义**:用户编号。同一身份证可能开多张会员卡,共享一个 `user_id`
- **取值约定**:租户内唯一
- **NULL 语义**:业务上不允许 NULL
- **单位 / 精度**:无
- **特殊值**:无
- **已知异常**:无

### 2.3 字段:`member_id`

- **类型**:BIGINT
- **业务语义**:会员编号。每张会员卡一个,一对多到 `user_id`
- **取值约定**:租户内唯一
- **NULL 语义**:业务上不允许 NULL
- **单位 / 精度**:无
- **特殊值**:无
- **已知异常**:
  - 同一个 `user_id` 下可能有多个 `member_id`(一户多卡模式)

### 2.4 字段:`member_status`

- **类型**:STRING
- **业务语义**:会员状态
- **取值约定**:业务约定的状态枚举(有效 / 注销 / ...)
- **NULL 语义**:理论上业务上不允许 NULL,但脏数据中可能出现
- **单位 / 精度**:无
- **特殊值**:`'cancel'` 表示注销(用于 `user_all_cancel_100001` 与 `cancel_stats` CTE 的过滤条件)
- **已知异常**:无

### 2.5 字段:`op_type`

- **类型**:STRING
- **业务语义**:操作类型,记录这条快照是新增、更新、还是删除
- **取值约定**:业务约定的操作类型枚举
- **NULL 语义**:业务上不允许 NULL
- **单位 / 精度**:无
- **特殊值**:`'-D'` 与 `'DELETE'` 都表示删除操作,**两种写法并存**
- **已知异常**:
  - **坑 1**:同一个删除语义存在 `'-D'` 和 `'DELETE'` 两种写法。SQL 里用 `op_type NOT IN ('-D', 'DELETE')` 兜底,而不是单一比较。**不能用 `op_type = 'DELETE'` 否则漏掉 `'-D'` 的脏数据**

### 2.6 字段:`deleted`

- **类型**:INT
- **业务语义**:逻辑删除标记
- **取值约定**:`0` = 未删,`1` = 已删
- **NULL 语义**:理论上不允许 NULL
- **单位 / 精度**:无
- **特殊值**:无
- **已知异常**:
  - **坑 2**:`deleted` 与 `op_type` 必须同时看。只用 `deleted = 0` 会漏掉 `op_type = 'DELETE'` 但 `deleted = 0` 的脏数据。两个条件是冗余校验,缺一不可

### 2.7 字段:`create_time` / `update_time`

- **类型**:TIMESTAMP
- **业务语义**:数据写入时间 / 数据更新时间
- **取值约定**:标准时间戳
- **NULL 语义**:理论上不允许 NULL
- **单位 / 精度**:秒级
- **特殊值**:无
- **已知异常**:
  - **坑 3**:同一会员可能有多个有效快照(`update_time` 不同时刻有多条记录),必须用 `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY update_time DESC)` 取最新
  - **水位线**:`DWS` 用 `date(create_time) <= '${dt}'` 做水位过滤,左闭右开

## 3. 跨字段约束(业务规则)

- **规则 A**:`tenant_id`、`user_id`、`member_id` 三个字段共同构成业务主键(三键去重必备,缺一不可)
- **规则 B**:`deleted = 0` AND `op_type NOT IN ('-D', 'DELETE')` 是"有效会员"的充要条件,任一不满足视为脏数据
- **规则 C**:注销状态判断(`member_status = 'cancel'`)只在 update_time 落在 `[月初, ${dt})` 区间内时才计入"本月注销"

## 4. 已知数据问题 / 坑

- **坑 1**:`op_type` 删除取值不统一(同时存在 `'-D'` 和 `'DELETE'`),过滤时必须 NOT IN 兜底
- **坑 2**:`deleted` 与 `op_type` 必须双校验,任一漏检都会带入脏数据
- **坑 3**:三键去重是必备:`tenant_id + member_id` 不足以唯一定位——同一个 `member_id` 可能挂在不同 `user_id` 下(虽然少见)
- **坑 4**:拉链表典型问题——同一会员有多条历史快照,必须 ROW_NUMBER 取最新
